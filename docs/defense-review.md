# Ревью предложения «навсегда закрепить диалог за Pod»

**Предложение коллеги:** закрепить диалог за Pod навсегда (sticky forever), чтобы
использовать локальный префиксный кеш. Ситуация: у реплики A есть нужный
префикс, но очередь 3 с; реплика B свободна, пересчёт префикса стоит 0,8 с.

## Решение при этих условиях

Отклоняю «навсегда» — при этих числах привязка прямо вредна. Полная цена
запроса у A: очередь 3 с + дешёвый hit (~0,1 с) ≈ 3,1 с. У B: очередь 0 +
miss (0,4 с в имитаторе; на реальном engine — prefill по префиксу) + пересчёт
0,8 с ≈ 1,2 с. B быстрее в ~2,6 раза. Постоянная привязка оправдана лишь пока
`queue(A) < cost(пересчёт на B) − экономия кеша`; она «привязана» к моменту
измерения и ломается при масштабировании, замене Pod и деградации A. Мгновенная
картина 3 с против 0,8 с — не основание для вечного правила.

## Недостающие измерения

1) Распределение очереди A/B во времени (p50/p95 за окно, а не момент):
   очередь на A может быть всплеском из-за одного клиента (см. опыт B:
   hot-клиент при ClientIP-привязке создал перекос >90%). 2) Доля повторных
   обращений к префиксу (hit-rate при sticky) — выгода привязки равна
   `(hit_cost − miss_cost) × hit_rate`; при 10% повторов выгоды нет. 3) Цена
   пересчёта на B при её реальной загрузке (пересчёт на свободной B ≠ на
   загруженной). 4) Стоимость балансировки без привязки на настоящем
   inference engine: префиксный кеш там дорогой (десятки–сотни мс prefill на
   тысячу токенов), и экономия может перевесить очередь — мерить надо на
   engine, а не на имитаторе. 5) Влияние привязки на горизонтальное
   масштабирование (новая реплика не получает клиентов — опыт C2).

## Допуск нового запроса

Новый запрос диалога не обязан ждать «свой» Pod: история передаётся в запросе
(messages) или лежит во внешнем хранилище, поэтому любой Ready-реплика может
обслужить. Закрепление — оптимизация выбора, а не условие допуска: запрос
направляется на B, если у A p95-очередь выше порога, и лишь помечает сессию
для будущей привязки после переобогрева кеша B.

## Восстановление диалога после потери A

Состояние диалога не в Pod (наш сервис: история в запросе; прод: внешнее
хранилище с session_id) — потеря A не теряет диалог. Привязка A→B
перестраивается автоматически: timeout sessionAffinity (наш стенд 10800 с)
или балансировщик по session_id. Проверка — checks.py `sessions`: диалог
продолжается после замены реплики, артефакт-версия стабильна.

## Правило для начатого потокового ответа

Активный стрим не переносится. (а) Штатное обновление: grace-period (30 с,
uvicorn graceful 25 с) даёт старым стримам завершиться — опыт A3: 0
оборванных; (б) внезапная смерть A (kill, опыт A5): стрим обрывается,
клиент повторяет запрос с тем же request_id на другую реплику (повторы
учитываются отдельными попытками); перенос «на лету» невозможен.
